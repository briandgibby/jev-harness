# Jev Orchestration Harness execution brief

## Mission

Build and test the command-line Jev Orchestration Harness in `outputs/jev-harness`. The authorized outcome is a fixture route → coding-model patch → trusted verification path, plus at least two distinct pinned local coding-model registrations and a watched Intel Arc Pro B70 inference path through OVMS 2026.4.0 on Windows. Jev performs one bounded typed routing judgment at a time. It stays in shadow mode until held-out routing evidence supports promotion. No model connects components, authorizes tools, or declares tests green. (JOH-1–JOH-8)

## Workflow and constraints

1. Work in `outputs/jev-harness`. Inspect current files before editing. The workspace is not a Git repository; do not claim Git status or publish anything. Preserve the original Jev adapter behavior. Mark a checklist item `[/]` immediately before implementation, and `[x]` only after its check ran and output was retained. Reconcile the packet and canonical PRD/PRS when code changes the design. (JOH-1, JOH-2, JOH-6)
2. Keep the implemented `orchestrate.py` commands `init`, `dry-run`, `demo`, `run`, `inspect`, and `replay` runnable. They create a complete generated simple or interval-merge task, strict config, tiny Git base, protected evaluator, isolated checkout, and run record. `--jev-mode off` is the clean rules-only control; fixture/live modes observe Jev or, behind an experimental flag, allow one Jev route. Finish missing direct broker/verifier/reconstruction interfaces only with checks that prove their contracts. (JOH-1, JOH-2, JOH-4–JOH-6)
3. Keep `local_model.py probe` and importable `chat_completion` bounded. `model-pins.json` owns the two model identities/revisions/artifact metadata; `orchestrate.py init` and `tools/setup_ovms.ps1` derive from it, and controller load checks drift. OVMS setup has `-Action dry-run|install|serve|verify -Model fast|strong`, pinned hashes, new-root refusal, and loopback binding. Both post-pin dry-runs and fast installed-root `verify` passed; fast install/serve were watched, while the strong script install/serve path remains untested. `tools/prepare_verifier.ps1` ships dry-run/install/verify for the pinned Docker image; dry-run/verify passed on this host. A 7B add response and separate 30B interval response are not a paired routing comparison. Fetch/load sequentially with a watched cap and record failures without fallback. (JOH-1, JOH-3–JOH-6)
4. Preserve the [direct OpenVINO device query](evidence/ovms-device-map.md) identifying `GPU.1` as Arc Pro B70, explicit `--target_device GPU.1` fast server command line on port 8766, and 7B response through that endpoint. Do not generalize this correlated host evidence to other devices or to the strong server. The controller still lacks an automatically checked per-run server/device/artifact receipt. (JOH-3, JOH-6)
5. The current controller applies strict JSON full-file content replacements to declared existing paths in an isolated checkout; it does not use `git apply`. The verifier runs protected evaluator code in the pinned Docker Python 3.14.6 slim image with no network, read-only root/checkout, all capabilities dropped, and no credential environment. A reproduced false-green path showed that candidate `os._exit(0)` could terminate the old evaluator before tests while returning exit zero. The current evaluator isolates candidate calls and requires a trusted test-count verdict. Retain the failing-then-passing regression and a new watched live run before asserting JOH-5 completion integrity; old records are rejected on replay. Preserve unedited outputs, exit codes, hashes, and terminal events. Before replacing a modified derived checkout, ship and test its reconstruction path. (JOH-4–JOH-7)
6. Review `README.md`, canonical PRD/PRS, checklist, and actual files before handoff. Finish [walkthrough.md](walkthrough.md) only from observed files/output. Run the packet validator with `--strict --require-walkthrough` after the final edits. Leave JOH-8 open until a held-out routing comparison runs. No commit, push, deployment, schedule, or broad unattended run is authorized by this brief. (JOH-1–JOH-8)

The first live scope is one generated task, one coding-model attempt, bounded output/time/path effects, and optionally one watched Jev shadow call after source admission. The current Jev adapter audits and may send its full input/request, so never pass raw source, logs, credentials, headers, or tool arguments to it without a separate approval policy. Provider and audit failures stop with a named next action. Local OVMS calls use validated loopback only; no inherited proxy, redirects, or silent CPU fallback. Every shipped component exposes a direct CLI; the planned broker/verifier split remains open. (JOH-2, JOH-4, JOH-6, JOH-7)

## Verification and deliverables

From `outputs/jev-harness`, run `python --version` and `python -B -m unittest -v` after code settles. Then run the exact shipped commands in the [plan's verification table](implementation_plan.md#verification-commands-and-evidence-plan): fresh `init`, `demo`, `dry-run`, setup-script dry-run and watched setup, `local_model.py probe`, one watched `run --mode live`, `inspect`, and `replay`. Retain each command's unedited output. Run `python -B orchestrate.py --help` and `python -B local_model.py --help` to verify registration. Add negative checks for forbidden egress, path traversal, model mismatch, missing runtime/device, failed or bypassed tests, and incomplete audit. Do not list `doctor`, `smoke`, or `generate` as existing commands. (JOH-1–JOH-7)

The deliverables are a usable CLI, two pinned locally exercised coding models, a bounded live coding attempt with independent check evidence, explicit Arc Pro B70 inference evidence or an honest incomplete gate, updated operator instructions, a reconciled packet, and an evidence-backed walkthrough. A smoke run is not a coding-quality benchmark; the [held-out study](../../coding-decision-study.md) controls any later Jev-superiority claim. (JOH-3, JOH-5, JOH-8)
