# Jev Orchestration Harness implementation plan

## Goal and verified current state

Build a directly callable CLI that routes one bounded coding task, invokes one of two pinned local coding models through OVMS, and accepts completion only after protected checks run. The [requirements pointer](PRD.md) links the canonical [PRD](../../PRD-Jev-Orchestration-Harness.md) and [PRS](../../PRS-Jev-Orchestration-Harness.md); the [checklist](task_checklist.md) tracks execution and the [brief](agent_prompt.md) carries this plan to an implementer.

## Decision points and dependency order

The initial provider is OVMS 2026.4.0 Windows binary, whose observed archive SHA-256 is `46d03114c97abfe05f2c5a8fde772c655aeef541ee254c23f402f81a616474e3`. Initial local registrations are the OpenVINO Qwen2.5-Coder-7B INT4 and Qwen3-Coder-30B-A3B INT4 artifact revisions fixed in the [PRS](../../PRS-Jev-Orchestration-Harness.md#52-coding-model-adapter). The 30B model requires a preflight resource check; OpenVINO recommends at least 19 GB of GPU VRAM. If its load fails, the requirement for two successfully exercised registrations stays open. Generated code will run only in a Docker Linux sandbox using `docker.io/library/python@sha256:b921fe7e7522f828d45197a47656ec465a9b15689b27fa8e1fba2864fca5b967`, no network, read-only root and checkout, and no Linux capabilities. The chosen host repository for later integration, real-project test corpus, reviewer identity, exact budgets, and Jev-promotion thresholds remain owner decisions; the generated fixture and first watched local task can proceed without treating those as settled.

1. Preserve `jev_harness.py` as the sole Jev transport and policy implementation. Add a strict orchestration schema and offline fixture first. The fixture needs no secret, network, model download, or manual state. (JOH-1, JOH-2, JOH-6)
2. Complete the bounded pinned OVMS preparation path for the strong registration and retain artifact, version, device, readiness, and one-response evidence. The fast script path has passed install and readiness on a separate root; model downloads remain explicit watched operations preceded by dry-run scope and size. Do not use `latest` or moving `main`. (JOH-3, JOH-4, JOH-7)
3. Harden the existing one-step route, full-file replacement, and independent verifier where the observed implementation differs from the intended Release 1 contract. In particular, preserve the direct broker/verifier/reconstruction surface implemented in `orchestration_tools.py`, and complete runtime pin verification and remaining Release 1 contracts. A coding model does not run arbitrary tools or set its own verdict. (JOH-2–JOH-7)
4. Exercise both registered models on the same bounded coding prompt, map Arc Pro B70 to `GPU.<index>` directly, and retain explicit-target server/device evidence for a non-fixture GPU call. The existing watched interval-merge 30B task proves only one branch and six protected checks. Keep Jev shadow-only until a held-out routing study qualifies it. (JOH-3–JOH-8)

## Integration traces and contracts

```text
orchestration_tools broker -> canonical task/config -> existing patch parser
                          -> pinned base + scratch restore proof -> scoped apply + receipt
orchestration_tools verify -> canonical task/config + broker receipt
                          -> base-plus-patch regeneration -> existing Docker sandbox + verdict
orchestration_tools reconstruct -> completed saved run + pinned Git base + patch
                               -> scratch hash proof + existing replay -> fresh source tree
orchestrate init -> generated config + task + Git fixture + protected evaluator
orchestrate demo -> admission -> BaselinePolicy -> fixture model patch
                 -> scoped apply -> independent verifier -> append-only run record
orchestrate run --mode live --jev-mode fixture|live --watch
                 -> admission -> eligible model set -> baseline route
                 -> optional Jev Choice observation or experimental route
                 -> local_model.chat_completion -> full-file replacement
                 -> pinned Docker verifier -> event/report record
setup_ovms.ps1 -Action dry-run|install|serve|verify -Model fast|strong
                 -> pinned archive/model checks -> GPU.1 OVMS loopback server
local_model.py probe -> one bounded loopback completion/response
prepare_verifier.ps1 -Action dry-run|install|verify
                 -> pinned Docker registry manifest/local Linux/amd64 image
```

`TaskManifest` is the sole task owner; a run keeps a hash-verified snapshot. `model-pins.json` owns both exposed IDs, exact HF revisions, expected artifact metadata, and parser names. `init` derives task registration copies with generation settings/endpoints, `load_state` rejects identity/revision drift, and the setup script reads the same owner and verified the installed fast bytes without mutation. The run ledger owns observations and links the existing Jev audit. The approved route feature packet excludes source, prompts, logs, URLs, headers, credentials, and tool arguments by default. The current `run_one` stores its full input/request and may send them to TypeSafe, so admission and egress checks precede it. `unclear`, ineligible, or threshold-failing Jev outputs cannot execute. A live Jev-controlled route currently requires an explicit experimental flag; do not call this promoted routing. A provider, disk, audit, runtime, or verifier failure stops with a code and next action. (JOH-2, JOH-3, JOH-6, JOH-7)

The local adapter is constrained to a validated loopback address and one OVMS text-generation endpoint. It checks readiness and the exposed model ID, sends one request with a configured maximum output token count and timeout, and validates one non-streaming response. It records model and device evidence separately: a Windows adapter name or generic `GPU` string is not proof of Arc Pro B70 execution. Resolve OpenVINO's device names to the Arc device before server start and require `GPU.<index>` for the GPU smoke. [OVMS parameters](https://docs.openvino.ai/2026/model-server/ovms_docs_parameters.html), [OpenVINO device naming](https://docs.openvino.ai/2026/openvino-workflow/running-inference/inference-devices-and-modes.html). (JOH-3, JOH-4, JOH-6)

The current executor accepts a strict JSON artifact with full UTF-8 contents only for declared existing files. It rejects symlinks, absolute/traversal paths, test/evaluator writes, oversize content, and undeclared tool effects; it does not call `git apply`. The verifier uses the generated manifest's protected evaluator inside the pinned Docker image with `--network none`, `--read-only`, `--cap-drop ALL`, no credential environment, and read-only checkout/evaluator mounts. It captures unedited stdout/stderr and exit codes, and refuses `completed` when the check is missing, failed, altered, or timed out. A scratch base-tree restore proof runs before the first file write. `orchestration_tools.py reconstruct` now regenerates a completed run into a new destination after a scratch proof and historical replay; canonical audit/task/model records are never overwritten. (JOH-4–JOH-7)

## Compatibility, safety gates, and recovery

The existing TypeSafe config schema and tests remain untouched. New orchestration configuration has its own schema version; no new fields are injected into `jev_harness.validate_config`. The adapter constructs a valid immutable Choice config and passes only approved state. The external OVMS contract comes from [OpenVINO's Windows quickstart](https://docs.openvino.ai/2026/model-server/ovms_docs_llm_quickstart.html); the TypeSafe contract remains owned by the existing harness. Unknown response fields can be preserved in restricted raw evidence, but required fields, model identity, and usage are validated before continuing. There is no retry or fallback after a provider failure. (JOH-2, JOH-3, JOH-6)

Triggered gates: sensitive data/authorization (operator-approved source and provider fields, no credential egress); untrusted input (strict JSON, paths, patch and output bounds); external API provenance (OVMS and TypeSafe response contracts); durable state (exclusive writes and tested reconstruction); compatibility (unchanged Jev adapter); interactive CLI behavior (success, review, missing dependency, timeout, and recovery output). Concurrency, streaming, production deployment, and high-stakes decision authority are outside Release 1. No first run is wide or unattended: fixture reads are safe; each model download and live call has a dry-run and watched cap. (JOH-1, JOH-4, JOH-6, JOH-7)
